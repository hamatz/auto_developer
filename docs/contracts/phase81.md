### 1.1 Phase 80 の後に分かったこと

Phase 80 の完了後の確認では、過去の 10 ステップで Red-First の確認を試し、9 ステップが `CONFIRMED` だった。一度は「`enforce` に切り替えてよい」と判断したが、その後の調べで、この結果は信頼できないことが分かった。

- **サンドボックスの中で git が動かない。** 候補テストに渡す環境から、名前に `KEY` を含む変数を秘密として除いている。そのため、ホストに `GIT_CONFIG_COUNT=1`・`GIT_CONFIG_KEY_0`・`GIT_CONFIG_VALUE_0` があると、`GIT_CONFIG_KEY_0` だけが消える。git は `missing config key GIT_CONFIG_KEY_0` で終了コード 128 になる（Linux で確かめた）。
- **macOS でも、サンドボックスの中の `git init` が終了コード 128 で失敗している。** Phase 80 の後の監査の AUD-1008（P1）は、再現テストが `git init` で失敗し、`REJECTED` になった。原因は macOS の側ではまだ確かめていない。ホームディレクトリの読み取りの禁止（SBX-1）で、git がホストの設定を読めずに止まっている可能性がある。
- このリポジトリのテストの多くは、準備（`setUp`）で一時的な git のリポジトリを作る。そのため、チェックポイントのコードと関係なく失敗し、`CONFIRMED` になる。実際に、Phase 80 で足したテスト `tests/test_audit8_chunk_completeness.py` は、通るはずのコミット（966114c）に対しても `CONFIRMED`（`SETUP_ERROR`）になった。
- 試した 13 ファイルの `CONFIRMED` の理由は、例外・読み込みの失敗・準備の失敗だけで、アサーションの失敗は0件だった（IDEA-038）。

**このため、このリポジトリの `enforce` への切り替えは、Phase 81 の後に試し直してから決める**（Phase 80 の完了後の記録の判断を取り消す）。

## 3. 設計の判断

### 3.1 ホストの `GIT_*` をすべて除く（SBX-9）

`GIT_CONFIG_COUNT` だけを足して除くのではなく、`GIT_` で始まる変数をすべて除く。理由は2つある。

- `GIT_CONFIG_*` の組（数・キー・値）は、どれか1つが欠けると git が止まる。組の一部だけが残る形をなくす。
- `GIT_DIR`・`GIT_WORK_TREE`・`GIT_INDEX_FILE` が受け継がれると、候補テストの中の git のコマンドが、一時クローンではなく元のリポジトリを指すおそれがある（git のフックの中から `verify-step` を呼んだ場合など）。サンドボックスが書き込みを止めるとしても、候補テストに元のリポジトリの場所を教える理由はない。

`HOME` と `XDG_CONFIG_HOME` は、一時領域の中の空のディレクトリにする。ホームディレクトリを読ませない（SBX-1）ことは変えず、git がホストの設定を読もうとして失敗する形をなくす。

### 3.2 今のコードでの成功の確認（GATE-18）

Red-First の確認で本当に知りたいのは、「失敗の原因が、そのステップの変更の前後の違いにある」ことである。チェックポイントで失敗するだけでは、サンドボックスの中だけで起きる失敗（今回の git のような環境の違い）と区別できない。

同じサンドボックスで、今の作業ツリーのコードに対しても実行し、**チェックポイントで失敗し、今のコードで通る**ときだけ `CONFIRMED` にする。環境が同じなので、差は変更による。IDEA-038（`import` の失敗だけで Red になる）も、この形でおおむね解ける。新しい関数を読み込むテストは、今のコードでは読み込めて、中身のアサーションまで実行される。

- 実行の時間は、対象のファイルあたり最大で2倍になる（1回 120 秒まで）。対象は Red-First のタスクで変えたテストのファイルだけなので、許容できる。
- 全体の結果は、今と同じく「どれか1つのファイルが `CONFIRMED` なら `CONFIRMED`」とする。1つのステップで、新しいテストのファイルと、既存のテストの資料の手直しを一緒に変えることがあるため（手直しした側は `NOT_RED` になる）。
- `enforce` では、`NOT_GREEN` も検証の失敗にする。検証スクリプトでは通るのにサンドボックスで失敗するテストは、テストが環境に依存しているので、人間が見るべきである（Fail-Closed）。

### 3.3 ファイル名の扱い（RCV-9・AUDIT-10・GATE-19）

この種類の不具合は、これで4回目になる。

- AUD-1004（GATE-11）: 秘密を含む名前のファイルの検査。
- AUD-1006（AUDIT-8）: 監査の組の差分から、日本語の名前のファイルが抜ける。
- AUD-1009（AUDIT-10）: pathspec の記号を含む名前のファイルが、ほかのファイルにも当たる。
- RCV-9（今回の確認で見つけた）: 隔離のときの秘密の検査が、日本語の名前のファイルを飛ばす。

1つずつ直すだけでは、また同じことが起きる。Lauren の講演の「人が直したくなったら、それを CI の規則にする」に従い、規則をテストにする（GATE-19）。テストは、`src/auto_developer/` の Python のコードを静的に調べ、`--name-only`・`--name-status` を含む git の呼び出しに `-z` がないものを失敗にする。`git status --porcelain` は、変更の有無だけに使う箇所が多いので、テストの対象にはせず、名前を使う箇所だけをこのステップで直す。

RCV-9 の重さ: 隔離ブランチは手元のブランチで、プッシュはしない。それでも、秘密を Git のオブジェクトに残さない（RCV-7 は、秘密を含むファイルを隔離ブランチに入れない設計）ことが崩れるので、P2 として扱う。手元で、追跡している `鍵.txt` に秘密鍵の形の文字列を入れると、検査で除かれずに残ることを確かめた（`key.txt` は除かれた）。

保護ファイルの検査（INV-1）は、日本語の名前のファイルでも検知できていた（表示が引用符と8進数の形になるだけ）。GATE-19 で、表示もそのままの名前にする。

## 4. 影響分析

### 4.1 SBX-9・SBX-10（ステップ 1・2）

- **指紋**: `verifier.py` の `RedTestVerifier` の環境の組み立て（`SECRET_ENV_PATTERN`・`DANGEROUS_ENV_PREFIXES` の後、`PYTHONPATH`・`TMPDIR` を設定している所）。一時クローンを作る所の `(resolved_repo / ".git").is_dir()`。
- **既存テスト**: 候補テストの実行を確かめるテストは約 28 ファイルある。ホームディレクトリの読み取りを確かめるテスト（`tests/test_red_verifier.py` など）は、ホームのパスを親のプロセスで求めて候補テストに埋め込んでいるので、`HOME` を変えても影響しない見込み。候補テストに渡る環境そのものを確かめているテストがあれば、`GIT_*` と `HOME` の期待を変えてよい（アサーションの趣旨は変えない）。
- 監査の再現テスト（AUDIT-2 の P0・P1）も同じ仕組みで動くので、git を使う再現テストが実行できるようになる。

### 4.2 GATE-18（ステップ 3）

- **指紋**: `verifier.py` の `verify_red_first_tests`・`_classify_red_first_file_result`。`cli.py` の `verify-step` の Red-First の分岐（警告と `RED_FIRST_NOT_CONFIRMED`）。`review-input` の `red_first.json`。スキル `/nightly-run`。

### 4.3 RCV-9・AUDIT-10（ステップ 4）
