## 1. このフェーズの目的

v0.10.0 のリリース前の独立監査で、次のことが分かった（PLAN.md の 2026-11-27 の記録）。

- 監査の入力が約 60 万トークンになった。起点から対象までの差分の全体（テスト・ドキュメント・GIF の行を含む）を渡していたため。1回目は、監査役が考える段階で出力の上限を使い切り、結果を出す前に打ち切られた。
- 上限を上げた2回目は、指摘0件で通った。ただ、監査役が考えた量は約 2,000 トークンと、入力に比べて非常に短かった。量が多すぎて、表面しか見ていない可能性がある。
- 監査だけの実行の報告が「0 / 3 件のタスクが正常に完了」となり、失敗のように見えた。

独立監査は、Auto Developer が「Maker と Checker の外からもう一度見る」ための仕組みである。入力が大きすぎて働かないなら、その保証は形だけになる。このフェーズで、監査の入力を絞って分け、監査の深さを報告で見えるようにする。

あわせて、BACKLOG の小さな修正を2つ行う。

## 3. 設計の判断

### 3.1 既定の範囲（AUDIT-6）

監査役の役目は、実装が SPEC に反していないか、安全の関門に抜け道がないかを見ることにある。テストは実装の正しさを確かめるもので、監査役が読めば役に立つこともある。ただ、このリポジトリでは差分のうちテストが大きな割合を占め、入力を倍以上にしていた。既定ではテストとドキュメントを外す。テストも見せたい場合は、`--audit-paths` で明示する。

このリポジトリの場合、既定の範囲はおおむね `src/` と `scripts/` と設定のファイルになる。v0.9.0 から v0.10.0 までの差分では、約 370KB（約 10 万トークン）。

### 3.2 分割の上限（AUDIT-7）

既定の上限は 200,000 バイト（およそ 5 万トークン）とした。v0.9.0 の監査（入力約 25 万トークン）では P2 の指摘が2件出たが、v0.10.0（約 60 万トークン）では考えた量が極端に短かった。1回の依頼の入力を小さくすれば、組ごとに注意を向けやすくなるはず、という見込みによる。根拠は経験の2点だけなので、値は設定で変えられるようにし、このフェーズの後に v0.10.0 の範囲で監査をやり直して、組ごとの考えた量を確かめる（人間の作業）。

ファイルの途中では分けない。1つのファイルの変更を2つの依頼に分けると、どちらの監査役も全体を見られなくなるため。

各組の依頼には、ほかの組のファイルの一覧を書く。監査役が「このファイルの呼び出し先は、別の組にある」と分かるようにするためである。組をまたぐ欠陥（あるファイルの変更が、別の組のファイルの前提を壊すもの）は、分割すると見つけにくくなる。これは分割の代償として受け入れ、報告の監査の深さの節に、組の数を必ず示す。

### 3.3 監査の深さ（RPT-8）

「入力 1 万トークンあたり、考えた部分が 100 トークン未満」を、弱い保証の目安にする。v0.10.0 の監査は、入力約 60 万に対して考えた部分が約 2,200 で、1 万トークンあたり約 36 トークンだった。この目安は判定を変えない（`SUCCESS` は `SUCCESS` のまま）。人間に注意を促すだけである。目安の値は経験が少ないので、今後の監査の記録を見て直す。

### 3.4 互換性（AUDIT-7）

`audit_stage.json` は Bundle に入り、`verify-bundle` が照合する（BDL-4・AUDIT-1）。v0.10 までの記録（`chunks[]` がない）は、これまでどおりに確かめる。最上位の `provider_request_id` には1組目のものを入れ、これまでの読み手が壊れないようにする。

## 4. 影響分析

（`compile --impact` に相当する検索を手で行い、テストの名前と行を確かめた。）

### 4.1 AUDIT-6・AUDIT-7（ステップ 1・2）

- **指紋**: `audit.py` の `audit_repository`（`git diff <起点> <対象>` の全体を渡している）と `audit`、`build_audit_prompt`、`last_run_metadata`。`cli.py` の全体のオプション（`--audit-baseline` の隣）。`bundler.py` の監査の検証（`provider_request_id` の確認）。
- **既存テストへの影響の見込み**: `audit_repository` を呼ぶテストは、`tests/test_audit_provenance_and_release.py`、`tests/test_independent_audit_runner.py`、`tests/test_level7_real_loop_e2e.py`、`tests/test_live_claude_audit.py`、`tests/test_metrics.py`。このうち、テストの資料の差分が `tests/`・`docs/`・`*.md` だけを変えていて、監査役が呼ばれることを期待しているものは、既定の範囲では範囲が空になる。そうしたテストは、資料の変更を範囲の中のファイル（例: `src/` の下）に移すか、`--audit-paths` を指定してよい。アサーションは変えない。`diff_sha256` が範囲で絞る前の差分の SHA-256 であることを確かめているテストがあれば、止まって報告する。
- **免疫テスト**: 監査に関わる免疫テスト（`tests/immunity/test_immunity_audit_budget.py` など）は変更しない。失敗した場合は止まって報告する。

### 4.2 RPT-8（ステップ 3）

- **指紋**: `reporter.py` の要約（「件のタスクが正常に完了」）、「あなたに判断してほしいこと」の節、監査の節。`brief` の監査の表示。
- 既存テストで、監査だけの実行の報告の文言を確かめているものは、調べた範囲では見つからなかった。失敗した場合は止まって報告する。

### 4.3 RCV-8・CMP-15（ステップ 4）

- **変えてよい既存テスト**:
  - `tests/test_rcv7_quarantine_git_object.py` の、案内の形（`git cat-file -p <SHA> > <パス>`）を正規表現や完全な一致で確かめている行は、新しい形（`mkdir -p` と引用符）に合わせてよい。取り出した中身が元と一致することの確認は変えない。
  - `tests/test_cmp4_compile_impact.py` の、`mock_tests` が出ないことを確かめている行（Phase 77 のステップ 2 の時点の確認）は、空の一覧が出ることの確認に変えてよい。
