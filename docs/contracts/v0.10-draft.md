## 1. 目的

**Auto Developer を、「良い SPEC を書ける人」以外にも使えるようにする。**

v0.9.0 で、「入力された SPEC と PLAN を、検証と査読を通して確実に実行する」部分は固まった。ボトルネックは入力の側に移っている。

- Phase 70 で止まった原因のほとんどは、SPEC のあいまいさ（SBX-6、GATE-5、GATE-7）と、影響分析の漏れだった。
- それを埋めていたのは、人間と設計セッション（Elephant）が手で書いた契約書（影響分析、「既存テスト変更の理由」）だった。新しい利用者には、この役がいない。

v0.10 では、次の2つを用意する。

1. **Spec Compiler**: EGM の設計書から SPEC・PLAN・`teams.json`・契約書の**下書き**を作り、Phase 70〜71 で人間が手でやった点検を機械で行う。論文の言う「引き継ぎ（handoff）」の段階を機械にするものである。
2. **ダッシュボード**: 承認された計画の構造の上に、実際の記録から進み具合を重ねて表示し、人間が「何が起きて、何を判断すればいいか」を一目で分かるようにする。

## 2. 守ること（不変条件の候補）

v0.10 の機能は、次の2つを新しい不変条件として SPEC に加えることを提案する。

- **INV-11 表示は記録から**: ダッシュボードとその元になる状態のスナップショットは、Auto Developer 自身が書いた記録（`events.jsonl`、Evidence と査読の記録、ジョブとチームの状態、Git）だけから作る。エージェントが進み具合を自己申告で書いたファイルを、表示の元にしない（INV-10 と同じ考え方。Phase 67〜69 では、自己申告の判定が実際の出力と食い違っていた）。
- **INV-12 Spec Compiler は契約を書かない**: Spec Compiler は SPEC.md・PLAN.md・`teams.json`・免疫テストを直接書き換えない。下書きを `.dev/compile/` に出力し、人間が読んで承認し、人間がコミットする。SPEC は人間が承認した契約である、という原則は変えない。

## 4. 要件の案

### 4.1 GATE-11 機密のファイルの検査の修正（Phase 72）

- `SECRET_FILE_IN_COMMIT` の検査は、ファイル名を `-z`（NUL 区切り）で読み、日本語などを含むファイル名も判定する（AUD-1004）。
- 種類の変更（`T`: シンボリックリンクから通常のファイルへ、など）も「変更」として扱う（AUD-1005）。

### 4.2 STAT ダッシュボード（Phase 72、74）

- **STAT-1 状態のスナップショット**: `auto-dev status --json` が、次をまとめた1つの JSON を出力する。読むのは INV-11 の記録だけ。
  - 単一チーム: 計画のタスクとその状態、各タスクの検証・査読・コミットのイベント（時刻、判定、モデル）、隔離ブランチ、判断待ちの事項（PLAN.md の「止まっていること・判断待ち」）。
  - チーム: ジョブの状態、チームごとの worktree・ブランチ・タスクの進み具合・`NO_CHANGES`・隔離、統合の結果（`integration/<job_id>`、`rc/<job_id>`）。worktree ごとの記録（`.dev/evidence/`）もまとめる。
  - 独立監査の結果、Bundle の検証の結果（あれば）。
  - スナップショットの形式には版（`schema`）を付け、ダッシュボードはそれを確かめる。
- **STAT-2 ダッシュボード**: `auto-dev dashboard` が、STAT-1 の JSON を読んで表示する1枚の HTML を作る。標準ライブラリだけで作る（外部の依存を増やさない）。
  - 表示の中心は「止まっている箇所とその理由」と「人間が判断すべきこと」にする。緑の成功より先に、隔離・`SANDBOX_UNAVAILABLE`・判断待ち・Checker の REJECT を目立たせる。
  - main への取り込みはしない（RC タグまで）ことを、表示でも正しく示す。存在しない機能（文書の自動同期など）は表示しない。
  - 更新の方法（7.2 の決定: サーバーなし。`--watch` で HTML を書き直す）。
- **STAT-3 計画の構造を重ねる**（Phase 74）: Spec Compiler の IR があれば、要件 → ステップ → チーム → コミット → 査読のつながりを表示し、要件から元の設計書の行までたどれるようにする。

### 4.3 CMP Spec Compiler（Phase 73、74）

- **CMP-1 中間表現（IR）**: EGM の設計書の構造を、そのまま IR の形にする（5 章）。どの要素にも、元の文書の場所（ファイル・行の範囲・その部分の SHA-256）を付ける。
- **CMP-2 取り込み**: 2つの経路で IR を作る。
  - EGM の設計書（`docs/designs/*.md`）: 見出しの対応（5.1）で取り込む。Goldfish の査読を通ったものとして扱う。
  - 文書群（`goal.md`, `architecture.md`, `decision.md`, `todo.md` など）: 5.2 の対応で、1つの設計書の形に組み立てる。**未査読**として扱い、文書どうしの食い違いを洗い出したうえで、Maker と別の系統のモデルの査読を通るまで、下書きを出さない。
  - IR の下書きを作るのは LLM の仕事なので、スキル（`/nightly-compile`）の側で行う。CLI は、IR の形式の検査と、以下の決定的な点検だけを行う。
- **CMP-3 決定的な点検**（`auto-dev compile --check <ir.json>`）: 6 章の点検を行い、ERROR があれば下書きを出さない（終了コード 1）。
- **CMP-4 影響分析**: 既存のリポジトリに対して、要件ごとの影響を機械で洗い出す。CLI の入口の列挙、要件に書いた「旧挙動の指紋」の構文木（AST）での検索、判定の目印やキャッシュをモックしているテスト、記録を合成しているテスト。結果から「既存テスト変更の理由」の候補を作る（docs/contracts/phase71.md の 6 章の手順の機械化）。
- **CMP-5 下書きの出力**（`auto-dev compile --emit`）: `.dev/compile/` に、契約書・SPEC の「## 5.」の節・PLAN の「## ステップ」と「既存テスト変更の理由」・`teams.json`・受入テストの案を出す。既存のファイルは書き換えない（INV-12）。
- **CMP-6 スキル**: `/nightly-compile` が、設計書を読み → IR を下書きし → `compile --check` を通るまで直し → 別系統のモデルに IR を査読させ → `--emit` して → 人間に契約書を渡す。
- **CMP-7 追跡と食い違いの検出**: SPEC の要件と PLAN のステップに、元の設計書の場所と SHA-256 を残す。設計書が後で変わったら、`compile --check` が「設計書と SPEC の食い違い」として報告する（EGM のプラグインの「設計書とコードの食い違いの報告」を補う）。
- **CMP-8 実物での確認**: `docs/designs/autonomous_pipeline_orchestrator.md` を入力にしたテストを置く。5.3 の食い違いを検出することを確かめる。ad-team-trial の電卓（`examples/two-teams/`）も、設計書の形に起こして入力にする。

（7.1 の決定: `compile --check` は関門にせず、勧めるだけにする。）

## 5. 中間表現（IR）の形

### 5.1 EGM の設計書の見出しとの対応

| 設計書の節 | IR の要素 | 行き先 |
| --- | --- | --- |
| Overview / The Problem | `purpose` | 契約書の目的、SPEC の概要 |
| Glossary | `terms[]` | SPEC の用語。定義のない用語の点検 |
| Goals | `requirements[]` | SPEC の要件 |
| CUJs（Given / When / Then） | `acceptance[]` | 受入テスト（E2E）の案 |
| Non-Goals | `out_of_scope[]` | SPEC のスコープ外 |
| Architectural Decisions | `decisions[]` | 不変条件の候補、判断の記録 |
| Technical Plan / Detailed Implementation Plan | `steps[]`, `files[]` | PLAN のステップ、チームの `owns` の案 |
| Verification Plan | `verification` | 完了定義、検証スクリプトの案 |
| Alternatives Considered | `alternatives[]` | 契約書（判断の理由）。SPEC には入れない |

### 5.2 文書群との対応

| 文書 | 設計書の節として |
| --- | --- |
| `goal.md` | Overview / Goals / Non-Goals |
| `architecture.md` | Technical Plan |
| `decision.md` | Architectural Decisions / Alternatives Considered |
| `todo.md` | Detailed Implementation Plan（どの要件にもつながらない項目は点検で報告） |
| 足りない節（CUJ、Verification Plan など） | 点検で ERROR。推測で埋めず、人間に聞く |

### 5.3 実物の設計書で見つかる食い違いの例

`docs/designs/autonomous_pipeline_orchestrator.md` には、点検で見つけるべき食い違いがすでにある。

- Goals では、失敗時に `git reset --hard` と `git clean -fd` で初期化するとしている。Decision 4 は、それを廃止して隔離ブランチに退避するとしている。CUJ 2 には、両方の書き方が混ざっている。
- Verification Plan は `pytest` を使うとしているが、実際の検証スクリプトは `unittest` で動いている（設計書と実装の食い違い）。

## 6. 点検の一覧（CMP-3、CMP-4）

Phase 70〜71 で、人間が手でやった点検をそのまま並べた。ERROR は下書きを出さない。WARN は契約書に載せて人間に判断を求める。

| ID | 点検 | 重さ | 由来 |
| --- | --- | --- | --- |
| L-1 | 各要件に、観測できる受入条件（終了コード、出力、ファイル）が1つ以上ある | ERROR | 完了定義 |
| L-2 | 「A または B」のような条件で、それぞれの場合の扱いが決まっている | WARN | SBX-6（Phase 70 で Checker の判断が往復した） |
| L-3 | 同じ要件の中で、「行う」と「行わない」が同じ対象を指していない | ERROR | GATE-5（DX-7 の範囲の食い違い） |
| L-4 | 用語の章にない用語を、要件で使っていない | WARN | Glossary |
| L-5 | 要件どうし、要件と判断（Decisions）、要件と不変条件（INV）が食い違っていない | ERROR | 5.3 の例 |
| L-6 | 既に実装済みの要件（SPEC 4 章）と同じことを言っていないか／変えるなら「修正」と明示しているか | WARN | Phase 70 の修正の4件 |
| L-7 | チームの `owns` が重なっていない。どのステップのファイルも、いずれかのチームの `owns` に入っている | ERROR | TEAM-1 |
| L-8 | どの要件にもつながらないステップ（todo）がない | WARN | 文書群の経路 |
| L-9 | フェーズの途中で SPEC を変えなくて済むよう、未決の点（「要検討」「TBD」など）が残っていない | ERROR | Phase 70 のタスク 3 の Bundle |
| I-1 | 要件の指紋（関数名・コマンド名・判定の目印）を、構文木で検索し、該当する既存テストを列挙する | 情報 | phase71.md 6 章 |
| I-2 | 判定の目印・キャッシュ・呼び出し回数をモックで作ったり確かめたりしているテストを列挙する | 情報 | SBX-6 |
| I-3 | 記録や Bundle の形式を変える要件では、記録を合成しているテストを列挙する | 情報 | BDL-4 |
| I-4 | CLI の入口（`auto-dev`、`python -m`、スクリプト、`main()`、スキル、README）を列挙する | 情報 | Phase 68〜69 |

LLM の判断に頼るもの（L-2、L-3、L-5 の一部）は、決定的に判定できる部分（同じ ID・同じ対象の語の出現など）だけを CLI で行い、残りはスキルの査読に回す。CLI の点検で、確信できない場合を ERROR にしない（LESSONS「静的解析は、確信できないなら安全側に倒し、完全を目指さない」）。

## 7. 決めてほしい点（2026-11-23、5点とも提案どおりに決定）

1. **`compile --check` を `/nightly-run` の関門にするか**: 案 A は、`/nightly-run` を始める前に、SPEC と PLAN が点検を通ることを必須にする。案 B は、点検を勧めるだけにする（v0.10 では B、利用が安定したら A、を提案）。
2. **ダッシュボードの更新の方法**: 案 A は、`auto-dev dashboard --watch` が数秒ごとに HTML を書き直し、ブラウザは自分で再読み込みする（サーバーなし）。案 B は、`auto-dev dashboard --serve` が標準ライブラリの HTTP サーバーで、JSON を配信してページが取りに行く（localhost だけ）。案 A の方が単純で安全なので、まず A を提案する。
3. **IR をリポジトリに残すか**: 承認した IR（`docs/designs/<name>.ir.json`）をコミットすると、追跡（CMP-7）とダッシュボード（STAT-3）の元になる。残す場合、IR は保護ファイルに加えるのがよい（人間が承認した計画の構造なので）。
4. **IR の下書きを、Antigravity 以外からも作れるようにするか**: `/nightly-compile` はエージェントのスキルなので、Antigravity などのエージェントが前提になる。`run --maker-cmd` と同じように、`compile --drafter-cmd` で外部のモデルを呼べるようにするかどうか（v0.10 ではスキルだけ、を提案）。
5. **出力の言語**: SPEC・PLAN・契約書の下書きを、入力の設計書の言語に合わせるか、日本語に固定するか。

## 8. 影響とリスク

- 既存の挙動は変えない（GATE-11 を除く）。Spec Compiler とダッシュボードは、新しいコマンドとスキルとして加える。
- 一番の危険は、Spec Compiler の下書きを人間が読まずに承認すること。契約書の先頭に、ERROR / WARN と、人間が判断すべき点を必ず並べる。また、下書きのまま `/nightly-run` に渡せない形にする（INV-12、`.dev/compile/` に出すだけ）。
- IR の形式は一度決めると変えにくい。`schema` に版を付け、Phase 73 の最初に形式だけを固める。
- 設計書の見本が1つしかない。EGM のプラグインの出力の形が変わっても動くよう、見出しの対応（5.1）を設定で変えられるようにする。
