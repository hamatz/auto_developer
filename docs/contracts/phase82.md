## 3. 設計の判断

### 3.1 Red-First の確認を一時クローンで実行する（GATE-20）

Phase 81 の後に、Red-First の確認の誤りが3種類残った。

- **未追跡のファイルの写しの漏れ**（AUD-1010）: 新しいディレクトリの中のファイルが写されず、今のコードでの実行が `IMPORT_ERROR` になる。手元で、`src/newpkg/mod.py` を足した正しいステップが `NOT_GREEN` になることを確かめた。SBX-11 で直す。
- **自明な Red の判定の誤り**（IDEA-042）: 監査の再現テストのための判定を、そのまま使っている。ファイルの単位で、AST の決めつけで、正しい Red を `NOT_RED` にする。
- **macOS の入れ子のサンドボックス**（IDEA-043）: サンドボックスの機能のテストは、サンドボックスの中からもう一度サンドボックスを起動できず、`NOT_GREEN` になる。

2つ目と3つ目は、Red-First の確認を、監査の再現テストのための仕組み（SBX）に乗せたことから来ている。監査の再現テストは、監査役（外部のモデル）が書いた、信頼できないコードなので、サンドボックスが要る。一方、Red-First の対象のテストは Maker が書いたもので、**同じテストを、検証スクリプトがサンドボックスなしで手元で実行している**。Red-First の確認だけをサンドボックスに入れても、安全の水準は上がらず、環境の違いによる誤りだけが増える。

そのため、Red-First の確認は、一時クローンの中で、検証スクリプトと同じ環境で実行する（人間が決めた）。

- 元のリポジトリを変えないことは、実行の前後の状態の比較で確かめる（`REPO_MODIFIED`）。サンドボックスで止める代わりに、変えたことを見つけて止める。
- 自明な Red の判定は使わない。GATE-18 で「チェックポイントで失敗し、今のコードで通る」を確かめているので、`assert False` だけのテストは、今のコードでも失敗して `NOT_GREEN` になる。AST の決めつけより、実行の前後の差の方が確かな証拠である。
- 監査の再現テストは、これまでどおりサンドボックスで実行する（SBX-1 は変えない）。

### 3.2 テストの書き方の規則を静的なテストにする（GATE-21）

PLAN の作業手順の【手順】の行のうち、次の3つは、テストのコードを読めば守っているかが分かる。

- `git init` には `-b <ブランチ名>` を付ける（今、約 55 か所が守っていない）。
- Python 3.10 にないモジュールを使わない（CI の 3.10 で初めて分かる）。
- 秘密鍵などの目印を、ソースにそのまま書かない（CI の gitleaks で初めて分かる。今、2か所がそのまま書いている）。

GATE-19（ファイル名の読み方）と同じく、静的なテストにする。CI まで待たずに、手元の検証スクリプトで止まるようになる。守っていない約 57 か所は、このステップで直す（ブランチの名前を足す、目印を組み立てる、だけの機械的な変更）。

`git init` の規則は、GATE-20 とも関わる。テストを実行する環境の `init.defaultBranch` の設定によって、既定のブランチの名前が変わる。名前を指定しないテストは、環境によって結果が変わりうる。

この後、PLAN の作業手順の【手順】の行は 15 から 12 になる（次のフェーズの準備で印を付け替える）。

### 3.3 検証スクリプトの雛形（DX-16）

`init` が作る雛形には、今、設定の行（DX-13 の `verify-timeout`、GATE-16 の `red-first`）がなく、利用者は設定できることに気づきにくい。また、v0.11-draft の 2.2 の「プロジェクトの規則を検証スクリプトに移す」ための場所がない。

- 設定の行は、既定の値のまま、意味の注釈とともに置く（挙動は変わらない）。
- 「プロジェクト固有の規則」の段は、注釈にした例だけを置き、既定では何もしない。利用者が、人が手で直したくなったことを、この段に検査として足していく場所にする（Lauren の講演の考え方を、利用者のプロジェクトでも回せるようにする）。

### 3.4 このフェーズでやらないこと

- このリポジトリの `enforce` への切り替え（このフェーズの後に試し直してから、人間が検証スクリプトを変える）。
- `run` / `teams run` の経路の Red-First の確認。
- テーマ T（チームの専門化）。Phase 83 以降。

## 4. 影響分析

### 4.1 SBX-11（ステップ 1）

- **指紋**: `verifier.py` の、一時クローンに未コミットの変更を写す処理（`_sync_uncommitted_files`。`git status --porcelain -z` を `-uall` なしで読んでいる。6d0956b の 1508 行の付近）。
- **既存テスト**: 変更しない。監査の再現テストと Red-First の確認の両方の写しが、新しいディレクトリの中のファイルを含むようになる。

### 4.2 GATE-20（ステップ 2）

- **指紋**: `verifier.py` の `verify_red_first_tests`・`_classify_red_first_file_result`（今は `RedTestVerifier.verify_red_first_test` を呼んでいる）。`cli.py` の `verify-step` の Red-First の分岐とメッセージ。`review-input` の `red_first.json`。スキル `/nightly-run`。
- **既存テスト**:
  - `tests/test_gate16_red_first_config.py`・`tests/test_gate17_red_first_exec.py`・`tests/test_gate18_red_first_current_green.py` は、サンドボックスを前提にした期待（`SANDBOX_UNAVAILABLE` の扱い、サンドボックスを使えない環境でのスキップなど）と、自明な Red の判定による `NOT_RED` の期待を、GATE-20 の判定に合わせて変えてよい。「チェックポイントで失敗し、今のコードで通るときだけ `CONFIRMED`」を確かめる趣旨は変えない。
  - 監査の再現テストのテスト（`tests/test_red_verifier.py`、SBX の各テスト）は変更しない。失敗した場合は止まって報告する（監査の再現テストの経路を変えていないことの確認になる）。

### 4.3 GATE-21（ステップ 3）

- **既存テスト**: `git init` にブランチの名前がない約 55 か所（6d0956b の時点。例: `tests/test_audit_lesson_recording.py`、`tests/test_bundler.py`、`tests/test_gate10_secret_commit.py`）に、ブランチの名前を足してよい。名前は、そのテストが後で使う名前（`main` か `master`）に合わせる。目印をそのまま書いている2か所（`tests/test_nightly_orchestrator.py`、`tests/test_rcv6_quarantine_snapshot_listing.py`）は、実行時に組み立てる形に変えてよい。アサーションは変えない。
- 免疫テスト（`tests/immunity/**`）は、保護ファイルなので、静的なテストの対象から外す。

### 4.4 DX-16（ステップ 4）

- **指紋**: `cli.py` の `DEFAULT_VERIFY_SH`。
- **既存テスト**: 雛形の文字列を確かめている `tests/test_dx5_python_selection.py`・`tests/test_gate14_protect_design_irs.py` などは、段の見出しの番号（`[1/2]` → `[1/3]` など）の期待を変えてよい。保護ファイルの検査の内容とテストの実行の内容を確かめるアサーションは変えない。
- README の `init` の説明は、人間が書く（README は人間の書く契約）。
