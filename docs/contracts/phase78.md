## 3. 設計の判断

### 3.1 失敗の数え方（GATE-15）

INV-4 は「同一タスクで検証または査読の失敗が2回続いたら止める」。低レベルのコマンドの経路では、タスクが成功すれば `commit-step` でコミットされて終わるので、「最後にコミットされた（または隔離された）後の失敗の数」が、そのまま「続いた失敗の数」になる。

- `task_start`（`pre-flight`）では数え直さない。数え直すと、`pre-flight` を呼び直すだけで INV-4 を避けられてしまう。
- 隔離（`rollback_step`）で数え直す。隔離の後に、人間の指示で同じタスクをやり直すことはある（Phase 73〜75 で何度も行った）。
- 判定の決まらない査読（出力が途中で切れた場合など）は数えない。GATE-13 で、1回の実行し直しを認めているため。2回続けて判定が決まらない場合に止まるのは、今は手順のまま（スキルの文言）。
- 止めたときの `verify_step` のイベントは、失敗に数えない結果（`FAIL_FAST_STOPPED`）にする。数えると、止まった後の呼び出しのたびに失敗が増えるだけになる。
- 記録が読めない場合は止めない。INV-8（計測は関門の結果を変えない）に従う。この検査は記録に依存するので、記録を壊せば避けられる。ただ、記録を壊す操作は、別の検査（保護ファイル、Evidence）に当たる。完全さよりも、今の誤り（手順の読み落とし）を防ぐことを優先する。

### 3.2 ミリ秒の時刻（STAT-12）

STAT-9 の「最小の間隔」は、同じ秒のイベントを記録ファイルの順に並べていた。2チームのデモは1秒以内に終わるので、先に読んだチームのイベントがすべて先に並び、並行に見えなかった。統合のイベントはリポジトリの記録にあり、それを先に読むと統合が最初に来ていた。本当の順番で並べるには、時刻を細かく記録するしかない。

`ts` の型（整数の秒）を変えると、既存の記録と読み手（テスト、Bundle）に影響するので、`ts_ms` を別の項目として足す。古い記録（`ts_ms` がないもの）は、今までどおりに並ぶ。

## 4. 影響分析

（Phase 77 の `compile --impact` に相当する検索を、手で行った。）

### 4.1 GATE-15（ステップ 1）

- **指紋**: `cli.py` の `verify-step` と `commit-step`、`metrics.py` の `count_verify_attempts`（数え方の参考）と `record_event`。
- **既存テストへの影響の見込み**: 同じタスクで2回以上失敗した後に、さらに `verify-step` や `commit-step` を呼んで、成功を期待している既存テストは、止められるようになる。調べた範囲では、`tests/test_metrics.py` の `test_verify_step_failed_and_attempt_increment` は、失敗の2回目で終わっている（3回目を呼んでいない）ので影響しない見込み。**ほかに失敗した場合は、変更せずに止まって報告する。**
- 免疫テスト（`tests/immunity/test_immunity_checker_policy.py` など）は、1つのタスクで失敗は1回まで。変更せずに通ること。

### 4.2 STAT-12（ステップ 2）

- **指紋**: `metrics.py` の `record_event`（`"ts": int(time.time())`）、`status.py` の時系列の組み立て、`dashboard.py` の `_build_replay_payload`。
- **変えてよい既存テスト**: イベントの項目の集合を、完全な一致で確かめている既存テスト（`tests/test_stat4_events_run.py` など）は、`ts_ms` を期待の集合に加えてよい。ほかのアサーションは変えない。
- STAT-9 のテスト（`tests/test_stat2_dashboard.py` などの、手で作った時系列のもの）は、`ts_ms` がない記録として、今までどおりに並ぶこと。

### 4.3 REL-6（ステップ 3）

- **変えてよい既存テスト**: `tests/test_version_consistency.py` の期待の版を 0.10.0 にする（v0.9.0 の REL-2 と同じ）。
- `docs/cli.md` に版が出る場合は作り直す。
