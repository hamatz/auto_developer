## 1. 2つの問い

### 1.1 マルチチームに意味はあるか

今のマルチチームが与えているのは、次の3つである。

- **並列実行**: 壁時計の時間が短くなる。ただし夜間に動かす前提では、速さはあまり効かない（元の設計書の Alternative 1 も、夜間の目的は速さではなく朝の信頼性だとして、並列を退けている）。
- **担当範囲の分離**（`owns`）: 範囲外を触ったら止まり、失敗もそのチームの中で隔離される。単一チームにない、本物の価値。
- **統合の関門**: 分けたことで生じるコストを払う仕組みで、利点そのものではない。

すべてのチームが同じ Maker・同じ Checker・同じ検証を使う限り、チームは「並列の枠」にすぎない。このリポジトリ自身も、77 フェーズのすべてを単一チームで開発してきた。

チームに分ける意味が出るのは、**チームごとに違うものを持たせたとき**である。

- 使うスキル（UI のチームはデザインシステムのスキル、データのチームはマイグレーションのスキル）
- Maker のモデル（得意な系統で分ける）
- Checker に追加で渡す基準（UI のチームの査読に、デザインシステムの文書を渡し、それに沿っているかを確かめさせる）
- チームごとの検証スクリプト

### 1.2 pstack と Auto Developer は何が違うか

Lauren の主張の芯は、「プロンプト・ルールの文書・スタイルガイドは柔らかい制約で、エージェントはすぐ忘れる。本当に効くのは、規則を静的解析と CI の赤信号に組み込むこと」だった。人が手で直したくなったら、そのたびに「これをどうやって lint や CI の規則にできるか」を問う。

一方、pstack そのものは、ワークフローのスキル・原則・プレイブック（Markdown）が中心で、それをエージェントに読ませる形になっている。Lauren 自身の主張に照らすと、pstack は「よい働き方を教える」側（柔らかい側）にある。

Auto Developer は、反対側にいる。

- 検証を通らなければ Evidence が出ず、Evidence がなければコミットできない（GATE-2・3）。
- 保護ファイルを触れば止まる（INV-1）。
- 査読の判定は Checker の出力から機械で読み、記録されていない査読があれば見える（GATE-5〜7・13）。
- 失敗した作業は消さずに隔離する（INV-3・RCV-1・7）。

つまり Auto Developer は、**エージェントの働き方そのものに対する CI の赤信号**であり、「その働き方で本当にやったか」の証拠（Evidence と Bundle）を残す層である。pstack のようなスキル集と競合するのではなく、組み合わさる。スキル集は Maker と Checker がどう働くかを教え、Auto Developer はその結果を機械で確かめる。ここに Auto Developer の生存領域がある、と考える。

### 1.3 自分たちの経験も、同じことを示している

Phase 70〜77 で、PLAN.md の作業手順には、次のような「柔らかい規則」が増え続けた。

- `--timeout 1200` を付ける（Phase 73）→ DX-13 で機械にした
- 査読は検証の後に、記録しない査読を作らない（Phase 73 のタスク 5）→ GATE-13 で機械にした
- テストに Python 3.10 にないモジュールを使わない（Phase 73）→ 手順のまま
- 偽の秘密の目印は実行時に組み立てる（Phase 75）→ 手順のまま
- 検証の失敗と査読の不承認を合わせて2回で止まる（Phase 77 で逸脱）→ IDEA-031 で機械にする予定

機械にしたものは、それ以後破られていない。手順のままのものは、いずれ破られる。Lauren の主張は、このリポジトリの歴史でも確かめられている。

## 2. v0.11 のテーマの案

### 2.1 チームの専門化（T）

- `teams.json` に、チームごとの任意の項目を加える: 使うスキル（名前と版）、Maker と Checker のモデル（系統）、Checker に追加で渡す文書（デザインシステムなど）、チームの検証スクリプト。
- 実行のときに、各チームが実際に使ったスキル・モデル・追加の文書を、Evidence と査読の記録に残す。Checker は、そのチームの基準で査読する。
- Spec Compiler（`/nightly-compile`）は、要件から、チームの分け方とチームごとの持ち物を**提案**し、その理由を契約書に書く。分ける理由がなければ「単一チームを勧める」と提案する（**既定は単一チーム**）。決めるのは人間（INV-12。チームの分け方は計画の骨格なので、機械が決めない）。

### 2.2 柔らかい規則を硬い関門にする（G）

- **PLAN の作業手順の各行を、「機械で守っている」か「手順だけ」かに分けて示す。** 手順だけの行の数を、フェーズごとに減らす目標にする。
- **INV-4 を低レベルのコマンドの経路でも機械で守る**（IDEA-031。v0.10.0 のリリースの前に入れる）。
- **Red-First をツールが確かめる**: 今は「先に失敗するテストを書く」が手順（Maker の自己申告）である。`verify-step` が、そのステップで足したテストがチェックポイントの時点のコードでは失敗することを、サンドボックスで確かめる（SBX の仕組みを使う）。
- **言語やプロジェクトの規則を、検証スクリプトの側に移すための雛形**: `init` が作る検証スクリプトに、プロジェクト固有の禁止の規則（例: 特定の API の使用禁止、層をまたぐ import の禁止）を足す場所と例を用意する。

### 2.3 直した経験を規則に変える輪（L）

- Checker の REJECT の理由と、人間が止まって判断したこと（PLAN の「止まっていること・判断待ち」と記録）を集計し、同じ種類のものが繰り返されたら、lint の規則・免疫テスト・検証スクリプトの検査の**案**を出す（契約書の下書きと同じく、決めるのは人間）。
- 今の LESSONS.md と免疫テストは、この輪を人間が手で回したものである。これを道具にする。

### 2.4 Checker の質を測る（E）

- わざと欠陥を入れた差分の集まりを用意し、Checker がどれだけ見つけるかを測る。
- 評価であることを Checker に気づかせない（ディレクトリ名や課題の書き方を、実際の作業と同じ形にする）。評価だと分かると振る舞いを変えうるため。
- 判定する側には、Checker と別の系統のモデルを使う。
- 結果は、Checker のモデルや指示を変えたときの回帰の確認に使う。

### 2.5 スキル集との組み合わせ（S）

- pstack のようなスキル集を、Maker・Checker の役ごとに宣言して使えるようにする（2.1 の `teams.json` の項目、単一チームでは PLAN か設定）。
- 使ったスキル集の版を、Evidence に残す（何を教えた上での結果かを、後から確かめられるように）。
- 自前で大きなプレイブック集は作らない（スキル集の側に任せる）。

## 3. やらないこと

- チームの分け方やスキルの割り当てを、人間の承認なしに機械が決めること。
- Auto Developer 自身が、汎用のプレイブック集やコーディングの原則集を抱えること。

## 4. v0.10.0 のリリースへの影響

- README では、単一チームを主な使い方として前に出す。マルチチームは「担当範囲を分けて並行に動かす、上級者向けの機能（実験的）」として位置づけ、チームの専門化は v0.11 で取り組むことを書く。
- IDEA-031（INV-4 を機械で守る）は、リリースの前に小さなステップで入れる。

## 5. 決めてほしい点

1. v0.11 のテーマ（2.1〜2.5）の優先順位。案: G（硬い関門）→ T（チームの専門化）→ L（経験を規則に）→ E（Checker の質）→ S（スキル集）。G は今の利用者全員に効き、T と S は G の上に乗るため。
2. Red-First をツールで確かめる（2.2）のは、既存の利用者の手順を変える。既定で有効にするか、設定で選べるようにするか。
3. Checker の質の評価（2.4）を、このリポジトリの CI に入れるか（モデルの呼び出しの費用がかかる）、手で回すか。

### 6.2 T（チームの専門化）の分け方

- **Phase 83**: チームの持ち物（スキル・モデル・査読の文書・検証スクリプト）を `teams.json` に宣言し（TEAM-29）、宣言したファイルを守り（TEAM-30）、低レベルのコマンドの経路で使い（TEAM-31・32）、宣言したモデルで動いたことを確かめて記録する（TEAM-33）。
- **Phase 84 以降の候補**: `teams run` の経路でチームごとのモデルとコマンドを使う。`teams report`・ダッシュボードに持ち物を示す。Spec Compiler（`/nightly-compile`）が、チームの分け方と持ち物を**提案**する（既定は単一チーム。決めるのは人間）。ad-team-trial で、持ち物の違う2チームを実際に動かす。
