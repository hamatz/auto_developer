## 3. 設計の判断

### 3.1 欠落の検査（AUDIT-8）

AUD-1006 の直し方そのもの（`-z` で読む）だけでなく、「組に分けたものをつなげると、分ける前と同じになる」ことを毎回確かめる。ファイル名の読み方以外の原因（パスの扱い、改行の違いなど）で抜け落ちても、監査が `SUCCESS` で通らないようにするためである。Lauren の講演の「人が直したくなったら、それを CI の規則にする」の考え方を、このツール自身に当てはめたものでもある。

### 3.2 Red-First の確認の仕組み（GATE-16・GATE-17）

- **何を確かめるか**: そのステップで追加・変更したテストのファイルを、チェックポイントの時点のコード（ステップの変更の前）に対して実行し、失敗することを確かめる。失敗すれば、テストがそのステップの変更を確かめていることの、最低限の証拠になる。
- **どこで実行するか**: 監査の再現テストのために作った、候補テストの隔離実行の仕組み（SBX。`RedTestVerifier`。チェックポイントのコードの複製と OS のサンドボックス）を使う。新しく作らない。
- **何を Red とみなすか**: 監査の再現テストでは、import の失敗は「再現できていない」として扱う。Red-First では、まだない関数やモジュールの import の失敗も、正当な Red とする（新しい機能のテストは、たいてい import から失敗する）。自明な Red（`assert False` だけ）と構文の誤りは、Red とみなさない（既存の判定を使う）。
- **対象の宣言**: Red-First を求めるタスクかどうかは、PLAN の題名（`Red-First` か `Red:` を含む）で決める。このリポジトリの PLAN も、`compile --emit` の下書きも、この形で書いている。ドキュメントだけのステップなど、Red-First にならないタスクは、題名に書かなければ対象外になる。
- **既定は `warn`**: サンドボックスの中では、外部のプロセスや Git を使う E2E のテストが、本来の理由と違う理由で失敗・成功することがある。最初から `enforce` にすると、正しいステップを止めかねない。まず `warn` で記録を集め、誤りの少なさを確かめてから、このリポジトリで `enforce` に切り替える（Phase 81 以降で判断）。
- **`enforce` は検証の失敗**: `enforce` で確かめられなかった場合は、検証の失敗として数える。2回続けば、GATE-15 で止まる。

### 3.3 PLAN の作業手順の印（準備のコミット）

作業手順の各行に、【機械】（ツールが守る）か【手順】（エージェントが読んで守る）を付ける。【手順】の行の数を、フェーズごとに減らす目標にする（v0.11-draft の 2.2）。今回の準備では、私が今の行を分類した。

## 4. 影響分析

### 4.1 AUDIT-8・AUDIT-9（ステップ 1・2）

- **指紋**: `audit.py` の `audit_repository`（`git diff --name-only` でファイルの一覧を読んでいる）、`pack_audit_diff_chunks`、`run_audit_stage` の成功と失敗の分岐（`err_payload`）、`reporter.py` の監査の深さ。
- **既存テスト**: 変更しない。Phase 79 で作った分割のテスト（`tests/test_audit7_*` など）は、このフェーズで前のステップが作った資料と同じ扱いで、失敗の記録の形が増えたことに合わせて期待を足してよい。

### 4.2 GATE-16・GATE-17（ステップ 3・4）

- **指紋**: `cli.py` の `verify-step`（GATE-15 の検査の後、検証スクリプトの前）、`verifier.py` の `RedTestVerifier.verify_candidate_test`（`commit` の引数でチェックポイントを指定できる）、検証スクリプトの行の読み取り（DX-13 の `resolve_verify_timeout`）、`evidence.py` の Evidence の記録、`review-input`。
- **既存テストへの影響の見込み**:
  - `verify-step` を呼ぶ既存テストは約 120 か所ある。ほとんどは、計画のタスクの題名に `Red-First` も `Red:` も含まないので、対象外（Evidence に `SKIPPED` と残すだけで、イベントは書かない）になり、挙動は変わらない見込み。
  - Evidence の記録の項目の集合を、完全な一致で確かめているテストがあれば、`red_first` を期待に加えてよい。
  - 題名に `Red-First` などを含む計画で `verify-step` を呼んでいる既存テストがあれば、既定の `warn` で警告が出て、サンドボックスでの実行の時間が増える。結果（終了コード）は変わらない。失敗した場合は止まって報告する。
- **免疫テスト**: 変更しない。
