## 1. このフェーズの目的

1. **スキルを実際に使える形にする**（CMP-13）。Phase 76 の確認で、エージェントが要件ごとの元の場所の SHA-256 を求める方法がないことが分かった。補助のコマンドを加える。
2. **影響分析を機械にする**（CMP-4・CMP-14）。今まで、人間と設計セッションが契約書を作るときに手でやってきた「既存のどのテストやドキュメントに影響するか」の洗い出し（Phase 71 の契約書 6 章の手順）を、決定的な検索にする。下書きの契約書と PLAN の「既存テスト変更の理由」に、候補として載せる。Phase 70〜75 で何度も止まった原因（「既存テスト変更の理由」に書いていない既存テストの失敗）を、準備の段階で減らすためである。
3. **承認した計画の構造を見せる**（GATE-14・STAT-11・STAT-3）。人間が承認した IR を、保護ファイルとしてリポジトリに残す。ダッシュボードは、それと計画ファイルの要件の ID から、「どの要件がどこまで進んだか」と、設計書が承認の後に変わったこと（`DESIGN_DRIFT`）を示す。

このフェーズの後は、v0.10.0 のリリースのフェーズ（README、CHANGELOG、独立監査）に入る。

## 3. 設計の判断

### 3.1 影響分析は候補を並べるだけ（CMP-4）

影響の有無の判断（そのテストを変える必要があるか）は、意味の判断なので CLI ではしない。CLI は、指紋の語がどこに出てくるかを、漏れが少ない側に倒して並べる。並べたものを人間（またはスキルの中の LLM）が読み、「既存テスト変更の理由」を書く。Phase 75 の契約書 3.4 の方針（確信できない場合を ERROR にしない）と同じである。

指紋（`fingerprints`）は、IR の下書きを作る LLM が書く。何を指紋にするかの良し悪しが、影響分析の質を決める。スキルの手順で、「要件が変える関数・クラス・コマンド・オプション・判定の目印（`SANDBOX_UNAVAILABLE` のような文字列）を指紋にする」と書く（ステップ 1 か 4 で、スキルの文言を足す）。

Python 以外の言語のファイルは、文字列の一致だけで調べる。言語ごとの構文木の解析は、利用者が増えて必要になったら考える。

### 3.2 I-3 は IR 全体に対して1回

記録を合成しているテスト（Phase 70 の BDL-4 のときに、記録の形式を変えて大量に壊れたもの）は、どの要件にもつながりうるので、要件ごとではなく、IR 全体に対して1回だけ並べる。このリポジトリでは件数が多くなるが、記録の形式を変える要件のときにだけ読めばよい。

### 3.3 承認した IR の保護（GATE-14）

承認した IR は、ダッシュボードの要件の表示（STAT-11・STAT-3）の元になる。Maker が IR を書き換えられると、承認されていない要件や、元の場所の書き換えで、表示がうそになりうる（INV-11 の考え方）。そのため、`docs/designs/` の直下の `*.ir.json` を保護ファイルにする。下書きの IR は `.dev/compile/` に置き、人間が承認したら `docs/designs/` にコピーしてコミットする。

保護ファイルの一覧は、製品の側（GATE-1 の検査、`init` の雛形）と、このリポジトリの検証スクリプトの3か所にある。このリポジトリの検証スクリプトは保護ファイルなので、人間が準備のコミットで直す。SPEC の 2 章の保護ファイルの一覧は、実装が入った後の準備（リリースのフェーズ）で直す。

### 3.4 要件の ID の出どころ（STAT-11）

計画ファイルのタスクの題名は、最後の括弧に要件の ID を書く形になっている（このリポジトリの PLAN も、`compile --emit` の下書きも）。承認した IR がなくても、題名から ID を読めば、要件ごとの進み具合を出せる。IR があれば、要件の文と元の場所を足す。IR がない利用者（Spec Compiler を使わない人）にも、ダッシュボードの要件の表示が役に立つ。

`schema` は変えずに項目を足す。ダッシュボードは、項目がなければ要件の表示を出さない。

### 3.5 ダッシュボードの見た目（STAT-3）

Phase 73 で人間が承認した見本の構成は変えない。要件の ID の印と、上部の要約の数を足すだけにする。見た目は人間が目で確かめる（Phase 74 の STAT-10 と同じ）。

## 4. 影響分析

（この節は、このフェーズで作る `compile --impact` を使う前の、手での分析である。）

### 4.0 入口の列挙

1. `auto-dev compile`（`--anchor`・`--impact` を加える。`--emit` の出力を変える）、`auto-dev status`、`auto-dev dashboard`、`verify-step`・`commit-step`（保護ファイルの検査）、`auto-dev init`（雛形）
2. `python -m auto_developer.cli`、`scripts/nightly_orchestrator.py`、`main([...])` の直接呼び出し
3. スキル `/nightly-compile`（ステップ 1・5 で変える）
4. `docs/cli.md`（DX-4。ステップ 1・2 で作り直す）
5. `scripts/check_doc_commands.py`（DX-14）: スキルに `compile --anchor` などを書くと、検査の対象になる
6. README（このフェーズでは変えない）

### 4.1 CMP-13（ステップ 1）

- **指紋**: `compiler.py` の出力先の名前を決める処理、`teams.json` の下書きの `project`、`skills/nightly-compile/SKILL.md`。
- **変えてよい既存テスト**: Phase 76 で作ったテスト（`tests/test_cmp5*`・`tests/test_cmp10*` など）のうち、IR のファイル名が `.ir.json` で終わり、出力先や `project` に `.ir` が残ることを確かめているものは、新しい規則に合わせて期待を変えてよい。スキルの文言を確かめているテスト（Phase 76 のステップ 5）は、文言の変更に合わせて変えてよい。確かめる趣旨は変えない。

### 4.2 CMP-4・CMP-14（ステップ 2〜4）

- 新しい処理（例: `src/auto_developer/impact.py`）と、`compile` の引数。`--check`・`--outline` は変えない。
- **変えてよい既存テスト**: ステップ 4 で、Phase 76 のテストのうち、`contract.md` の「影響分析は人間が書く」の1行や、`plan.md` の「既存テスト変更の理由」の形を確かめているものは、新しい形に合わせて期待を変えてよい。
- テストでは、一時ディレクトリに小さなリポジトリ（`src/` と `tests/` と README を持つもの）を作り、指紋ごとに期待する候補が出ることを確かめる。このリポジトリ自体に対しては、件数を固定で確かめない（コードが変わるたびに変わるため）。

### 4.3 GATE-14（ステップ 5）

- **指紋**: `guard.py` の `PROTECTED_PATTERNS` と `BASE_PROTECTED_PATTERNS`、`cli.py` の `init` の検証スクリプトの雛形（`PROTECTED_DIFF` と `DIRTY_PROTECTED` の行）。
- 雛形の保護ファイルの行を確かめている既存テストは、調べた範囲では見つからなかった。失敗した場合は止まって報告する。
- 免疫テストは変更しない。

### 4.4 STAT-11・STAT-3（ステップ 6・7）

- **指紋**: `status.py` の計画のタスクの読み取り（`_read_team_plan_tasks`、`_build_backlog`）と `attention[]`、`dashboard.py` の payload と HTML。
- `schema` は `auto-dev-status/2` のまま。`schema` の値を確かめている既存テストは変わらない。
- ダッシュボードの既存テスト（`tests/test_stat2_dashboard.py` など）は変更しない。
