**Version**: `v0.10.0`
**Date**: 2026-11-27

変更の一覧は [CHANGELOG.md](../../CHANGELOG.md) を参照してください（英語）。

## このリリースの位置づけ

v0.10.0 の目的は、Auto Developer を「良い SPEC を書ける人」以外にも使えるようにすることと、夜の間に何が起きたかを一目で分かるようにすることです。

- **Spec Compiler**: EGM の設計書から、SPEC・PLAN・`teams.json`・契約書の下書きを作ります。下書きは人間が読んで承認し、人間がコミットします（Spec Compiler は契約を書きません。INV-12）。
- **再生できるダッシュボード**: 夜の作業を時系列で再生します。backlog のチケットがチームに渡って減っていき、検証と査読を通ったコミットが積み上がっていく様子を、1枚の HTML で見られます。

あわせて、このリポジトリ自身を Auto Developer で開発する中で見つかった穴を、いくつも塞ぎました。記録されない査読、隔離で消えるファイル、エージェントの手順に任せていた Fail-Fast です。

## 主な変更

- **Spec Compiler（`auto-dev compile` とスキル `/nightly-compile`）**:
  - `--outline` で設計書の見出しを読み取り、`--check` で中間表現（IR）の形式と決定的な点検を行います。点検するのは、受入条件の欠け、判断との食い違い、実装済みの要件との重なり、担当範囲、未決の点です。
  - `--impact` で、要件が既存のどのテストやドキュメントに影響しうるかを洗い出します。
  - `--emit` で、`.dev/compile/` の下に下書きを書き出します。
  - `/nightly-compile` は、設計書 → IR → 点検 → 別系統のモデルによる査読 → 下書き、の流れをエージェントに指示します。
- **ダッシュボード**:
  - `auto-dev status` と `auto-dev dashboard` を加えました。
  - `--enable` で、記録が書かれるたびにダッシュボードを作り直します。
  - `auto-dev demo --teams` で、2チームの夜を再生するデモが見られます。
  - 承認した設計（IR）があれば、要件ごとの進み具合と、設計書が承認の後に変わったこと（`DESIGN_DRIFT`）も示します。
- **査読と Fail-Fast の厳格化**:
  - `record-review` は、1回の検証に対して、判定の決まった査読を1回だけ記録します。
  - 検証の後に作業ツリーが変わっていれば、査読の入力を作りません。
  - 判定の決まらない出力も、履歴に残します。
  - 低レベルのコマンドの経路でも、2回続けて失敗したタスクは先に進めません。
- **隔離の改善**:
  - 隔離の後に、スナップショットにだけある新しいファイルと、その取り出し方を示します。
  - 機密に見えるために退避から外れていた新しいファイルは、Git のオブジェクトとして残すようにしました（以前は消えていました）。
- **そのほか**:
  - 検証の制限時間を、検証スクリプトの先頭の行（`# auto-dev: verify-timeout=<秒>`）で決められるようにしました。
  - README とスキルのコマンドを、CLI の定義と突き合わせる検査（`scripts/check_doc_commands.py`）を加えました。

## 以前の版からの移行

- **トップレベルのオプションの省略形は使えません**。`auto-dev --work ...` のような省略形は、`--work-dir` と正しく書いてください。
- **査読の手順**: REJECT を記録した後は、`verify-step` からやり直してください。同じ検証に対して、査読を記録し直すことはできません。スキル（`/nightly-run`）は更新済みです。
- **Fail-Fast**: 同じタスクで、検証の失敗と査読の REJECT が合わせて2回になったら、`verify-step` と `commit-step` が先に進みません。`rollback-step` で隔離してください。
- **保護ファイル**: `docs/designs/*.ir.json`（承認した IR）が保護ファイルに加わりました。`auto-dev init` で作った既存の `scripts/verify_local.sh` を使っている場合、同じ検査を検証スクリプトの側にも入れるなら、手で追記してください。
- **状態のスナップショット**: `status --json` の `schema` は `auto-dev-status/2` です。

## 既知の問題

- **マルチチームは実験的な機能です**。今は、すべてのチームが同じ Maker・Checker・検証を使うので、チームに分ける利点は、担当範囲の分離と並行の実行に限られます。チームごとのスキル・モデル・査読の基準は、v0.11 で検討します（`docs/contracts/v0.11-draft.md`）。
- `compile --impact` は候補を並べるだけで、テストを変える必要があるかどうかは判断しません。
- 負荷の高い環境では、時間に依存する一部のテストが失敗することがあります。
- リリース前の独立監査（`claude-opus-5-5`、LIVE、`f98c251` から `53d55a9` まで）の指摘は0件でした。ただし入力が約 60 万トークン（テストとドキュメントを含む差分の全体）と大きく、監査役が考えた量は短かったので、弱い保証として扱ってください。監査の入力を絞る・分ける改善を予定しています。
- 監査だけの実行（`--enable-audit`）では、`NIGHTLY_REPORT.md` に「0 / N 件のタスクが正常に完了」と表示され、失敗のように見えます。
